# Changes 2026-10-02 (local, unpublished)

_Translated from Russian; original: [ru/CHANGES_2026-10-02.md](ru/CHANGES_2026-10-02.md)._

What was done, how to verify it, and which of it is confirmed by measurements. All measurements are on an RX 7800 XT /
RADV; "weak CPU" means the same machine restricted with `taskset` to 4 cores / 8 threads.

## Performance and smoothness

### Steam Deck and weak GPUs: the release 0.1 path is the default again

For output other than 1080p (720p on the Deck, 1440p, 2160p), the whole game is again rendered at the preset resolution
(a patch at startup), as in 0.1. Live scaling kept post-processing at 1080p and copied the scene targets back and forth
every frame: on the Deck and a GTX 1060 this gave 7–8 FPS.

- The path is selected by the "Change resolution on the fly" setting (launcher, menu, `bbport.ini`
  `live_resolution=auto|0|1`, applied after a restart). **Auto** (was the default; since 10-03 the default is "off") enables
  live changes on discrete GPUs with 8+ GB of memory, except NVIDIA older than Turing: on the RX 7800 XT
  resolution and presets can again be changed in the menu on the fly, while the Steam Deck and GTX 1060 get the fast
  path. The decision is written to the log (`GPU: … live resolution changes on/off`); `BB_LIVE_RES=0/1`
  overrides everything.
- Changing the preset, the output resolution, or switching to TAA in the menu on this path is done via the
  "Apply and restart game" button.
- Depth/stencil of downscaled targets on GPUs without `VK_EXT_shader_stencil_export` (Pascal) is again
  full-size, without the 9-pass copy.

### Ragged frame times when GPU-bound (NVIDIA)

Two causes, both fixed:

1. Frame presentation (`vkAcquireNextImage`, `vkQueuePresent`) was executed on the game's vblank thread. When
   the GPU is loaded, these calls block (especially on NVIDIA), and the game's vblank events arrived
   unevenly. Presentation now happens on a separate `bb:Present` thread (`BB_PRESENT_THREAD=0` — the old
   behavior).
2. The GPU command thread ran ahead and stalled on random resources, and flips came in bursts. Now it
   runs ahead of the GPU by no more than `BB_FRAMES_AHEAD` frames (default 1; 0 — unlimited).

4K without an upscaler, ~78 FPS, slow camera pan (`Frame pacing` in the log, 5 s windows):

| | FPS | frame-time spread | p99 | frames > 1.5× median |
|---|---|---|---|---|
| before | 79.5 | 9.9 ms | 25.8 ms | ~125 |
| separate present thread | 79.4 | 5.9 ms | 25.0 ms | ~80 |
| + 1 frame ahead | 77.4 | **0.9 ms** | **14.6 ms** | **0** |

On the weak CPU (720p FSR 3 Performance, uncapped), the frames-ahead limit does not affect FPS (166 FPS at 0, 1
and 2), while the separate present thread gave +3.5% (160 → 166 FPS).

New `Frame pacing:` line in `BB_FRAME_STATS=1`: median, spread, p99 and number of spikes.

### The shader cache was disabled permanently (stutters on entering every new area)

At startup the pipeline cache compares the saved `Shader::Profile` with the current one. In the original
shadPS4, on a mismatch the cache is **closed for the entire session** and writes nothing; the profile file
stays the old one, so from then on the cache never works, and every session compiles all
shaders again. Today the profile changed (a flag for Pascal), and from ~12:16 the cache was
off for all runs — including the run near Ludwig's arena: in the stutter window there were 64 compilations taking 114 ms.

Now an incompatible cache is cleared and rebuilt (one rebuild, as after an update). In the
log: `Pipeline cache isn't compatible with current system: rebuilding it`. Verification: running
the route twice in a row — 241 compilations in the first run, 28 in the second.

The same stutter on leaving the arena (115 ms, a player's run): besides compilations, registration of 1057
textures and upload of 220 MB of images and 245 MB of buffers in a single frame (page protection 17 ms,
residency 10.5 ms, image creation 7.9 ms, the rest is copying). This part still
needs to be spread across frames or threads.

### CPU on weak processors

Profile (`perf`, 4 cores / 8 threads, 720p FSR 3 Performance, uncapped, walking): ~166 FPS,
the limit is the second pipeline stage (`bb:DrawRec`, 88–90% busy; the first stage waits on it ~40%).
The second stage's time is smeared across resource binding and draw recording; there is no single hot
spot. For the Deck and Haswell (cores roughly half as fast) this is on the order of 85–100 FPS — above 60, which
means the average FPS there is not CPU-bound. The main problem on weak CPUs is streaming stutters (see
"Tools").

- The Vulkan recording thread chose its busy-wait time based on the total number of threads on the machine, not
  those available to the process: under a core restriction it spun for 200 µs instead of 20.
- The second stage's wait now also depends on the number of cores (`BB_PIPE_SPIN_US`); it does not
  affect FPS (166.3–166.8 at 0, 50 and 200 µs), and was left shorter for machines with 8 threads.
- Readbacks (Relaxed; they protect faces from vertex "explosions"): in the same scene 166.4 FPS versus 166.3 with
  `BB_READBACKS=0` — they cost nothing, there is no reason to disable them.

## Stability

### Crash `Guest fault … 0x263b8e7` with the two-stage pipeline

`sceGnmSubmitDone` did not block the game if the command thread had already **parsed** all buffers
(`num_submits == 0`), even though the second pipeline stage and the deferred fence labels had not yet written memory.
The game freed objects carrying labels, and the late write corrupted the heap. Added a
`work_retired` flag: the GPU is considered idle only after the pipeline has drained and the labels have been written.

Verification: 40 minutes on 4 cores / 8 threads without a crash. The crash is rare (the old build on my machine
also survived 40 minutes), so the only confirmation will be the absence of the crash on your side.

## Image

- **Sharpness up to 2.0** (launcher, menu). Up to 1 it is the upscaler's own RCAS; above that, an additional
  RCAS pass over the finished frame (FSR 3, FSR 4, FSR 4.1.1, including 720p output on the Deck; TAA has its own).
- **Ctrl+click on a slider in the menu** now lets you type a number (previously the keyboard could only
  erase: SDL text input was not passed to the menu).
- **Flickering objects on NVIDIA GTX 10xx (Pascal)** — coffins on the bridge, etc. (shadPS4 PR #1644
  fixes this only on Turing and newer via barycentrics). For NVIDIA GPUs without
  `VK_KHR_fragment_shader_barycentric`, the recompiler now multiplies the interpolated value
  by 1 + 2⁻¹⁶ before converting it to an integer: 0.99999994 yields 1 again. I found this pattern in 27
  Bloodborne shaders; on AMD with it force-enabled (`BB_INTERP_INT_FIX=1`) the image is the same.
  **Needs testing on a GTX 10xx.** The shader cache will be rebuilt once for everyone (new version).
- **Shader recompiler fixes from recent shadPS4** (released after the version the port's code was
  taken from): `V_CVT_PK_U8_F32`, `V_BFM_B32`, `V_ALIGNBIT/ALIGNBYTE_B32` (a shift by 32 with zero
  alignment gave an undefined result), SCC carry in `S_ADDC/S_SUBB_U32`, 32-bit
  literals in 64-bit numbers, compute shader floating-point mode, P10/P20 selectors in
  `V_INTERP_MOV_F32`. The list is in `gpu/VENDOR.txt`. Such instructions occur in depth/shadow
  packing; a connection to the shadow bugs (shadPS4 #4384, #3465) is not confirmed — please check those spots.
- **TAA.** Tried: blending in tonemapped space, history clipping in YCoCg, variance
  clipping, reconstructing the current frame with a 3×3 filter. Compared in a single run with
  on-the-fly toggling (static camera and pan): none of the techniques gave a gain beyond
  the run-to-run variance; YCoCg clipping and the 3×3 filter were worse. The previous algorithm remains the
  default; the techniques are available for experiments (`BB_TOGGLE_FILE`, bits 51–54). I need an example
  of where exactly TAA is unstable (location, what is visible) in order to fix that specifically.

## Mods, patches, launcher

- **Mods tested in-game**: a mod that replaces menu text works (upper-case paths,
  wrapper folder). New: name case does not matter; `Mod/CUSA03173/dvdroot_ps4`,
  an archive's wrapper folder, and mods without `dvdroot_ps4` (directly `chr/`, `parts/`…) are accepted. In the log:
  `Mods: N game files replaced, M added`.
- **Third-party shadPS4 XML patches**: a `patches/` folder in the data directory, a "Third-party patches" group in
  the launcher, selection stored in `patches.json`. Details — [MODS.md](MODS.md).
- **60/90 FPS** no longer fail with `patch overlaps a relocation`: patches that replace pointers
  are relocated by the loader to the actual image base.
- **Launcher in English** (defaults to the system language; switcher at the top of the page).
- "FPS limit" caption: 0 — follows the display refresh rate, no higher than 120 Hz.

## Memory

15 cycles of "Quit game → Continue" (level reload), 720p FSR 3:

| cycles | process RSS | VRAM |
|---|---|---|
| 0 → 7 | +179 MB | +751 MB |
| 11 → 15 | +8 MB | +15 MB |

The growth tapers off: on repeated loads this is cache warm-up (pipelines, textures), not
an unbounded leak. `heaptrack` over 8 such cycles also found no sources that grow from
load to load (the large ones are allocated once at startup: page table 279 MB, texture
cache pool 92 MB). By design the texture cache frees memory only when it hits the VRAM budget. A 40-minute
run in a single location: RSS ~2.64 GB, VRAM ~4.29 GB the whole time, no growth. Not tested:
a long playthrough across many different locations (cache growth up to the budget is expected there) — this needs
a recorded route.

## Testing tools

- **Route recording**: `BB_PAD_RECORD=/path/route.txt` — F9 in-game starts and stops recording
  gamepad/keyboard input. `BB_PAD_REPLAY=/path/route.txt` + the word `replay` in `BB_PAD_FILE` —
  playback from the same moment. This way you can run a route once (from the lamp near Ludwig to
  another lamp) and then repeat it in stutter measurements. Playback is verified; starting recording
  with the F9 key cannot be checked automatically — please check it.

  How to record: rest at the lamp near Ludwig, go to the menu and "Continue" (the character will appear at the
  lamp), in the launcher under "Extra variables" set `BB_PAD_RECORD=/home/<you>/route.txt`, after
  spawning press F9, run to another lamp, F9. You will also need the save (the
  `user/savedata` folder) so that the start is at the same point.
