## 1. Two-stage GPU command processing pipeline

**Problem.** The GPU command thread (`shadPS4:GpuComm`) did everything itself: parsed PM4, selected
pipelines, bound resources and recorded draws. The other cores sat idle.

**Solution** (`vk_draw_pipe.h`, `vk_rasterizer.cpp`, `liverpool.cpp`):
- **Stage A** (`GpuComm`) parses PM4, tracks registers, selects the pipeline, copies small
  constants into a ring buffer and puts a packet into the queue.
- **Stage B** (`bb:DrawRec`) keeps a copy of the registers (in 32-dword blocks of changes), binds
  resources and records draws and dispatches.
- A 16 MB lock-free queue sits between the stages.
- Memory operations (EOP/EOS, WriteData, DmaData, flip signal) are executed on stage B strictly
  in order with the draws.
- Drains (stage A waits until B is empty) remain only where they cannot be avoided.

Enabled automatically with 8+ threads (`BB_DRAW_PIPE=0/1`). On 16 threads: 110.9 versus
83.9 FPS (+32%); on 8 threads (like the Steam Deck): 83.8 versus 71.0.

**Further optimizations:**

| Optimization | Toggle bit | Effect |
|---|---|---|
| Constant ring on stage A | 36 | +11% |
| Memo of render pass state (90% of draws continue the open pass) | 44 | +9% |
| Memo of texture sets by T# hashes (32768 slots) | 45 | +5.6%, then another +1.3% |
| Pipelined indirect draws and indirect dispatches | 46 | +1.4% |
| Cheap check of pending GPU writes (range merging, infrequent cleanup) | — | ~+4% |
| Copy-shader HLE as a single compute dispatch, merging within 64 KB | 43 | GPU: 2.1 → 0.6 ms |
| Allocation-free motion history tables | — | no change in FPS |

What we found out:
- The bottleneck is now stage B: it is busy ~85% of the time, about 2.8 µs per packet, with a flat profile.
- Stage A waits ~25% of the time — at the first drain after a long series of draws. The frame statistics
  now show the wait for each drain site.
- Object motion vectors cost about 10% FPS.
- Gave no gain and were reverted:
  - relaxing the barrier on packet handoff (+0.4%, risk of a missed wakeup);
  - memo of dynamic state: context registers change on almost every draw.
- The PGO profile was rebuilt for the new code.

## 2. Why upscaler presets barely changed the GPU load

It turned out that on the RX 7800 XT drawing the scene itself is cheap. Native 1080p without
the upscaler is 3.67 ms of GPU, while FSR 4 itself at 1080p output is about 1.4 ms. So FSR 4 Ultra
Performance loads the GPU more than native rendering. At ~145 FPS we are CPU-bound, and the GPU is idle about
a quarter of the time.

Two real problems were found and fixed:
1. **Lighting passes were always drawn at 1920×1080.** The check "can this pass be drawn at
   reduced resolution" looked at all eight target slots, not only at the pass's own
   targets. The extra slots held G-buffer textures that the pass reads. Toggle 47.
2. **Unnecessary resampling.** Every pass that read a downscaled target first stretched it to
   1080p — about 25 times per frame, 0.4 ms of GPU. Now the shader recompiler marks images
   that are read only via normalized sampling, and such passes read the downscaled
   copy directly. Toggle 48. Because the metadata format changed, the shader cache is
   rebuilt once on first launch.

GPU time per preset after the fixes (one process, `BB_PRESET_FILE`):

| Preset | GPU, ms/frame |
|---|---|
| Native AA | 5.72 |
| Quality | 5.35 |
| Balanced | 5.21 |
| Performance | 4.99 |
| Ultra Performance | 4.82 |

The next candidate for the Steam Deck is the guest compute copy `3d5ebf4e`. It copies render
target memory (1080p depth is 12 MB) and drags image downloads and uploads along with it. Its
replacement with image-to-image copies is described in parallel_gpu.md.

## 3. Crash after 13–17 minutes (corrupted guest heap)

**Symptom.** `Guest fault … at guest offset 0x263b8e7, address 0x5300000000`: the free list
of the guest allocator contained a corrupted pointer. It crashed only with the pipeline.

**How we searched.**
- Stress tests of 15–40 minutes (`tools/soak.sh`) and bisection with pipeline toggles.
- The guest memory write log `BB_WRITE_LOG=1` masked the race: even nanoseconds of
  delay on label writes hid it.
- The `BB_WRITE_LOG=2` mode helped: it records label addresses at command-parsing time, i.e. outside
  the race. The dump at the crash showed that the end-of-frame labels were located inside freed
  48-byte heap objects.

**Cause.** Stage A sent the "GPU idle" interrupt as soon as it had parsed all command
buffers. On it, `sceGnmSubmitDone` releases the game, which then considers the frame's work finished. But
the end-of-frame (EOP) labels were at that moment still waiting in the Vulkan recording thread
(RecorderFences mode). The game freed objects containing these labels, while another of its threads kept
updating them.

**Fix.** Before this interrupt, stage A drains the pipeline and waits for all pending
labels. The same is done before WriteData/ReleaseMem on compute queues and before rare
non-pipelined graphics commands. Result: before the fix, 7 crashes in 7 runs; after,
2 runs of 30 minutes without crashes, FPS unchanged.

## 4. 1440p/2160p output resolution and game effects

A new section in the in-game menu (Insert or L3+R3): "Resolution and effects (after restart)".
The "Apply and restart game" button restarts the game via run.sh.

**Output resolution** (`bbport.ini`: `output_res=2560x1440` or `3840x2160`):
- Via a patch, the game draws the scene at the preset's resolution derived from the output. For example, 4K Performance is
  1916×1078: exactly 1920×1080 is not possible, since the port treats that size as UI space.
- FSR 3 or FSR 4 upscales the frame to the output size. FSR 4 was added to this mode: its
  HDR output is copied into the UI image.
- The interface stays in the game's 1920×1080 coordinates, and the port rasterizes it directly at the output
  resolution, so it is sharp. The first attempt to patch the UI to the output size stretched it by a factor of
  1.5 — fixed.
- For a scene larger than 1080p, the community heap patch is added and the direct memory budget is increased
  (`BB_DMEM_MB`, default 5056 MB, run.sh raises it to 9152).
- Verified:
  - 1440p FSR 3 and FSR 4 Quality — about 150 FPS;
  - 4K FSR 4 Performance — about 230 FPS.

  The HUD is in place in both cases.
- FSR 4 at 1440p and 2160p output needs "2160"-tier models. `fetch_fsr4_assets.sh`
  now downloads them by default.

**Effects.** Toggled on and off by community patches from `patches/Bloodborne.xml`:
- chromatic aberration;
- depth of field (DoF);
- motion blur;
- SSAO;
- the game's own anti-aliasing;
- shadows from dynamic light sources;
- SSR reflections (off by default);
- skipping intro movies/logos;
- model detail (LOD -2…2).

Keys in bbport.ini: `effect_*`, `skip_intro`, `model_lod`.

## 5. Launcher (GTK4 / libadwaita)

Launch: `launcher/bb-launcher.sh` (if PyGObject/GTK4 is missing, it starts via
`nix-shell launcher/shell.nix`).

What it contains:
- **Game:** path to the game folder (checked for the presence of `eboot.bin`), saves folder, system language.
- **Display:** output resolution, fullscreen, frame presentation mode, HDR.
- **Upscaler:** selection, preset, sharpness, object motion vectors, FPS counter — the same
  bbport.ini keys as in the in-game menu.
- **Game effects** and model detail.
- **Frame rate:** patch (uncap/60/90/30) and FPS limit.
- **Performance:** GPU pipeline (auto/on/off), readbacks mode.
- **Developer:** MangoHud, frame statistics, GPU profile, Vulkan validation,
  arbitrary environment variables.
- A "Log" tab with the game's output, "Launch" and "Stop" buttons (the game and its helpers
  are stopped as a single process group).
- `--play` launches the game with saved settings without a window — for Steam Deck Game Mode.

The launcher's own settings are stored in `~/.config/bbport-launcher/settings.json`.

## 6. AppImage for the Steam Deck

Build: `bash build.sh && bash packaging/appimage.sh`. Result:
`dist/Bloodborne-bbport-x86_64.AppImage`, about 700 MB.

How it works:
- `packaging/default.nix` builds the package: prebuilt binaries, preparation scripts, patches, FSR 4
  models, the launcher with Python, GTK4, libadwaita, icon themes and Mesa Vulkan drivers.
- The nix-appimage bundler mounts the internal `/nix/store` via user namespaces — these are available in
  SteamOS. So SteamOS libraries do not conflict with the package's glibc.
- The host driver cannot be loaded into the game process, so the radv from the package is used
  (`VK_DRIVER_FILES`).
- Data is stored in `~/.local/share/bbport`: generated files, `user/` (saves and shader
  cache) and `bbport.ini`. Saves are separate from `native_probe/user`; they need to be copied.
- run.sh got the modes `BB_PREBUILT=1` (prebuilt binaries, no build and no nix-shell),
  `BB_DATA_DIR` (data directory) and `BB_GAME_DIR` (game folder).

Bugs found on the first run on a live system:
1. "no version information available / undefined symbol: , version". patchelf in the nix fixup phase
   corrupted the symbol versions of the game's non-PIE binary. Now the binary looks up its library via
   `$ORIGIN/gpu`, and patchelf is not applied to it.
2. "libSDL3.so.0: cannot open". Nix finds dependencies only among the derivation's inputs, but
   the binaries are built outside it. Now `appimage.sh` writes the store paths from RUNPATH into
   `packaging/runtime-paths.nix`, and the package takes them as inputs.
3. "FSR 4 unavailable: missing …_2160_pre.spv": the "2160"-tier models were missing (see section 4).

After these fixes the game launches from the AppImage (`--play`), and FSR 4 works at 4K output.
