Measurements — RX 7800 XT / RADV, restricted with `taskset` to 4 cores / 8 threads, Steam Deck settings
(1280×720 output, FSR 3 Performance, 640×360 scene), uncapped FPS. Test bench:

## Changing resolution on the fly — off by default

`live_resolution` with no value (new install, launcher, menu) now means "off":
for output other than 1080p — resolution patch at startup, as in 0.1. `auto` (GPU check) and `1`
must be selected explicitly. Tests: `test_run_settings`.

## AppImage without FSR 4.1.1 models

The models are extracted from AMD's DLL and are not included in the public package (as in 0.1): `packaging/default.nix`
includes `fsr4_411` only with `BB_PACKAGE_FSR411=1`; otherwise they are looked up in the data directory.

## Steam Deck: launch and texture garbage collector

- **The AppImage did not launch the game on NixOS** (exit code 127 with no message): `run.sh` read
  `live_resolution` via `sed`, which is not present in the AppImage environment. Now only bash built-in
  commands are used; test `test_live_resolution_without_sed_or_grep`.
- **Texture garbage collector on integrated GPUs** (`TextureCache::GarbageCollectImages`). The budget was computed
  as "all heaps minus 8 GB for the system" (~1 GB on the Deck), while usage was taken from the GTT heaps, which also hold
  the buffers backing guest memory (~4 GB). The collector was permanently in "aggressive" mode: on every
  command submission (~66 per frame) it evicted up to 40 textures unused for 2–3 frames, then
  re-uploaded them, and asynchronously wrote GPU-modified ones back to guest memory. Now on integrated
  GPUs the thresholds are a fraction of the driver's current budget (`VK_EXT_memory_budget`): collection from 70%, pressure from
  85%, critical from 95%. Logged under pressure: `Texture cache: memory pressure, …`.
  `BB_GC_BUDGET_MB=N` — the same rule with a given budget on any GPU (for testing on PC).
- **Writing an evicted texture back to guest memory is now synchronous**, while the pages are still
  protected. The deferred write arrived after protection was removed — on top of whatever the game had already
  written there (e.g. the heap after a location unload). A possible cause of `Guest fault 0x263b8e7` on
  the Deck during map streaming; **on PC this crash also occurred once in ~10 runs, its cause has not been
  found** (the memory-pressure threshold on PC is ~11 GB, the collector never gets there).

## Changing resolution on the fly is cheaper

Previously only 1920×1080 targets were downscaled; the game's half-resolution post-processing (960×540, including
the bloom chain with mip levels) ran at full size and resampled the scene color every frame.
On the Deck one such pass cost ~8.4 ms (versus ~1.4 ms with the resolution patch).

- 960×540 targets are downscaled by the same factor as the scene (ProxySize). The FragCoord recalculation in
  shaders does not change: 960/320 = 1920/640.
- Half-resolution mip chains: a separate downscaled copy per level (key — image and
  level); sampling a single level reads the copy, sampling the whole chain reads the native image after
  resampling.
- Toggle `BB_TOGGLE_FILE` bit 50 (`SceneHalfRes`) — the old behavior.
- `BB_SCENE_DEBUG`: additionally prints resamples (`Scene resolve/fill`) and full-size reads of downscaled
  targets with the reason (`Scene native read`).
- Test: `scene-resolution-test` — copy of mip level 2 of a 960×540 chain and its return to the native level.

Result on PC (4c/8t): GPU busy time of the live path 3.41 → 3.23 ms per frame, pass `5a619b89` —
320×180 instead of 960×540. The image matches the patch mode (bloom and fog are computed at
reduced resolution, as with the patch). Remaining: ~9 resamples and ~7 back-fills
of the 1080p scene color per frame (copies, `9a9cf8a9`, UI composition).

**Why the live path is still more expensive on the CPU:** the game assumes a 1080p screen and in the lighting
pass (`vs 8747a367`) draws 335 light sources instead of 42 with the patch (small light sources
are culled by screen size): 975 draw calls per frame versus 679. This is the game's own decision.

## TAA: flickering of thin distant objects

Window bars, railings and debris edges flickered: in the jitter phase where a thin object does not cover the
pixel center, the depth test rejected the history (in it the object is closer than the current background). Now,
with sub-pixel motion, such history is kept and clamped to the neighbors' color (as in TAA without
depth-based rejection). Toggle bit 55 — the old rule.

Metric: 30 consecutive frames with a static camera (`BB_PRESENT_DUMP_COUNT=30`), mean temporal second
difference of luminance (frame-to-frame flicker; smooth animation has almost no effect), ×1e-3:

| | mean | p99.9 |
|---|---|---|
| before (2 runs) | 0.367 / 0.381 | 23.2 / 22.0 |
| after (2 runs) | 0.266 / 0.293 | 12.2 / 13.1 |
| no TAA and no jitter | 0.428 | 16.8 |

Soft color clamping for static pixels and variance clipping did not reduce flicker
(variance clipping increased it). `taa-shader-test` tests: added "thin line missed by this
frame keeps history", "static disocclusion is clipped", "moving disocclusion is rejected".

## Upscalers: reconciliation with the 2026-10-02 audit

The audit looked at the GitHub version (`cc001f9`); against the local code:

- Native AA outside 1080p (2.1) — already fixed (`w > ow`).
- FSR 4 v07 and the HDR flag (2.2): the provider stores the context flags but does not read them — the flag has no effect
  on the result. On the patch path the input is indeed LDR (after tonemapping) — a limitation
  of the path itself.
- Sky (4.1) and the depth threshold of object vectors (4.4) — already fixed (rotation without translation,
  relative threshold, full depth precision).
- **Mip bias (4.7) — done:** in G-buffer passes (5+ targets) with a downscaled scene, the sampler LOD
  bias is log2(render / output) (−1 on the Deck); shadows, post-processing and UI are unchanged. In
  the log: `Upscaler: scene texture LOD bias -1.00`. Toggle bit 57.
- Not done: particle classification for jitter (4.2), history reset on camera cut (4.8).

## CPU on weak processors: measurement

Patch mode, 4c/8t, 209 FPS. Threads (% of one core, user + kernel): `bb:DrawRec` 72 + 14,
GPU command thread 56 + 20, `bb:VkRecorder` 72 + 1 (mostly time in RADV), the game's main thread
46 + 10, four draw preparation threads at ~20 each. Total ~545% of 800% busy: the limit is
the sequential chain "command thread → draw recording → Vulkan recording". Further gains require
parallelizing Vulkan recording (multiple command buffers) — a major rework, not started.
