# Uncharted: The Nathan Drake Collection — Technical Research for uncharted_pc

_Researched 2026-10-16. Scope: the PS4 collection (Bluepoint, 2015) as it applies to this native Windows port (original PS4 executables + HLE runtime + shadPS4-derived Vulkan renderer). Claims are linked inline. **Speculation** and **inference** are labelled. Several primary pages (GDC Vault PDF, Eurogamer/Digital Foundry, Wikipedia, orbispatches) could not be fetched from the research environment. In those cases the claim comes from search-engine extracts or second-hand reposts, and the text says so._

## Key takeaways for uncharted_pc

- **The PS4 target is 1080p60, not 1080p30.** Digital Foundry measured all three games at native 1080p with a mostly locked 60 fps and rare dips to about 55 fps ([PSLS summary of DF](https://www.playstationlifestyle.net/2015/09/27/uncharted-nathan-drake-collection-analysis)). The PS3 originals were 720p30. The port's "60 FPS like on PS4" default is correct. Any frame-rate-dependent logic was tuned at a 60 Hz step, not 30.
- **The `m_gfxEopTick` assertion is the Naughty Dog frame pipeline working as designed.** `FrameBegin` in `ndlib\render\fg-draw-mgr.cpp:234` recycles a per-frame parameter block and asserts that the GPU's end-of-pipe tick for that frame is already set ([shadPS4 #5038](https://github.com/shadps4-emu/shadPS4/issues/5038)). shadPS4 found two causes: (a) the flip event was signalled **before** the EOP fence packet that follows the flip NOP had executed ([PR #4882](https://github.com/shadps4-emu/shadPS4/pull/4882), [PR #5140](https://github.com/shadps4-emu/shadPS4/pull/5140)); (b) the GPU side fell behind while compiling shaders. The port's "wait instead of assert" patch fixes (b). The repo should also make sure (a) cannot happen: signal the flip only after the whole flip DCB has executed.
- **The thread and fiber names in NDC match Gyrling's GDC 2015 fiber job system.** Logs show `NdJobWorkerThread N` and `NdJob Fiber (512 KiB)` ([#5099](https://github.com/shadps4-emu/shadPS4/issues/5099), [#4352](https://github.com/shadps4-emu/shadPS4/issues/4352)). The talk's slides list 6 worker threads and 160 fibers (128 × 64 KiB stacks and 32 × 512 KiB stacks), according to search extracts of the [slides PDF](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf). `src/runtime_fiber.c` therefore carries the whole engine's job system. Fibers migrate between worker threads, so per-thread state must never be cached across a switch (the file already says this).
- **The Windows "red zone" hazard is likely relevant to the unexplained crashes (likely, not proven).** shadPS4 found that when a guest access faults (for example on GPU write-tracking page protection), Windows exception dispatch can write below the faulting thread's RSP. That overwrites the 128-byte SysV red zone that guest leaf functions use. This caused a reproducible NDC main-menu crash ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038), [PR #4802](https://github.com/shadps4-emu/shadPS4/pull/4802), [#4816](https://github.com/shadps4-emu/shadPS4/issues/4816)). This port also installs a vectored exception handler (`src/probe.c`) and runs guest code natively. That makes this a good candidate for the intermittent U2 streaming and U3 London-bar crashes. **(Speculation; needs testing.)**
- **The target version is 1.02, with signature-based patches.** Community patch and cheat databases only have entries for `APP_VER` 01.00 and 01.02, and the code offsets differ between them. The four main title IDs (CUSA02320/02343/02344/02826) share patch definitions. That suggests the executables are identical across regions for a given version (**inference**). No 60 fps or uncap patches exist for NDC, because the game already runs at 60. The existing patches are logo skip, dev menu and a U2 quit-to-menu crash fix ([illusion0001 XML](https://github.com/illusion0001/PS4-PS5-Game-Patch/blob/main/patches/xml/UnchartedTheNathanDrakeCollection-Orbis.xml)).
- **shadPS4 exposed huge buffer bindings that likely cost VRAM.** NDC binds buffer descriptors with `num_records = 0xffffffff`, which shadPS4 clamped to roughly 2.7 GiB device-local buffers ([PR #4882](https://github.com/shadps4-emu/shadPS4/pull/4882), [#4353](https://github.com/shadps4-emu/shadPS4/issues/4353), [#5038](https://github.com/shadps4-emu/shadPS4/issues/5038)). This is the most likely structural reason 4 GB cards run out of memory (**inference**).
- **Uncharted: Legacy of Thieves on PC teaches four lessons.** Mouse sensitivity must not depend on frame rate. Camera input sampling must be paced with the game frame, or the camera jitters. There should be a frame cap. Shader warm-up and VRAM budgeting must be visible to the user ([DSOGaming patch coverage](https://www.dsogaming.com/patches/uncharted-legacy-of-thieves-collection-november-4th-update-fixes-its-mouse-movement-issues/), [camera jitter](https://www.dsogaming.com/news/uncharted-legacy-of-thieves-collection-suffers-from-mouse-camera-stutters-and-here-is-how-you-can-fix-them/), [ResetEra DF recap](https://www.resetera.com/threads/digital-foundry-uncharted-legacy-of-thieves-the-df-pc-port-review-pc-vs-ps5-optimised-settings.645954/)).
- **There is still no official PC release of NDC as of 2026-10-16.** Press coverage of this project calls it the first way to play U1–U3 on PC outside emulation ([DSOGaming](https://www.dsogaming.com/news/uncharted-the-nathan-drake-collection-unofficial-pc-port-released/), [PCQuest](https://www.pcquest.com/gaming/uncharted-the-nathan-drake-collection-gets-an-unofficial-pc-port-after-god-of-war-3-remastered-12681497)). Bluepoint was closed by Sony in March 2026 ([Shacknews](https://www.shacknews.com/article/147938/sony-closes-bluepoint-games)).

## The Nathan Drake Collection on PS4

### Bluepoint's remaster work

- **Developer and timing.** Bluepoint Games did the port and Sony published it. It released on 7 October 2015 in Europe and 9 October 2015 in North America ([Uncharted wiki](https://uncharted.fandom.com/wiki/Uncharted:_The_Nathan_Drake_Collection)). Bluepoint CTO Marco Thrush said work began in June 2014, right after The Last of Us Remastered shipped. Development took about 15 months, with a peak team of 48 (13 engineers, 17 artists) ([PSLS](https://www.playstationlifestyle.net/2015/10/19/bluepoint-games-set-work-different-kind-project-began-work-uncharted-collection-june-2014/), [DualShockers](https://www.dualshockers.com/bluepoint-discusses-the-challenge-of-remastering-the-uncharted-trilogy-for-playstation-4/)).
- **Scope.** Thrush described the main challenge as getting "six years' worth of Naughty Dog's content and code" working on PS4 ([Stevivor](https://stevivor.com/news/bluepoint-games-talks-porting-uncharted-to-the-ps4/)). Bluepoint changed gameplay as well as assets: aim assist, cover, weapon toggling, grenades, pick-up radius, dynamic difficulty and larger enemy head hitboxes, plus a wider aiming-sensitivity range ([DualShockers](https://www.dualshockers.com/bluepoint-discusses-the-challenge-of-remastering-the-uncharted-trilogy-for-playstation-4/)). New modes were Explorer and Brutal difficulty, Speed Run mode with leaderboards, and Photo Mode. Photo Mode is described as derived from The Last of Us Remastered ([PlayStation Blog EU](https://blog.eu.playstation.com/2015/10/09/uncharted-the-nathan-drake-collection-all-the-new-features-and-modes-detailed/), [Uncharted wiki](https://uncharted.fandom.com/wiki/Uncharted:_The_Nathan_Drake_Collection)).
- **Disc budget.** All three games fit on one 50 GB Blu-ray. To get there, Bluepoint improved audio and video compression and dropped multiplayer assets, bonus content and the stereoscopic-3D movies. The credits are rendered at runtime instead of being pre-rendered video. These details come from an Eurogamer/DF interview, as relayed by search extracts of [PSLS](https://www.playstationlifestyle.net/2015/10/19/bluepoint-games-set-work-different-kind-project-began-work-uncharted-collection-june-2014/) (second-hand). Pre-rendered cutscenes ship as compressed video, and DF quotes mention visible compression artefacts ([NeoGAF DF thread](https://www.neogaf.com/threads/digital-foundry-uncharted-the-nathan-drake-collection-is-more-than-just-a-remaster.1099794/page-8)). This is why the port has a video-decoder path (Videodec2) and plays movies "one video frame per vblank" (see `gpu/shadps4/core/libraries/videoout/driver.cpp`).
- **Multiplayer.** There is none, only the single-player campaigns. Owners did get access to the Uncharted 4 multiplayer beta in December 2015 ([GamingTrend](https://gamingtrend.com/news/access-to-uncharted-4s-beta-will-only-be-available-through-nathan-drake-collection), [PlayStation Blog](https://blog.playstation.com/?p=166419)).

### Engine lineage

- **PS3 origins.** U1 (2007), U2 (2009) and U3 (2011) ran on Naughty Dog's in-house PS3 engine, and much of the work ran on the Cell's SPUs. For U1, Christophe Balestra listed scene bucketing, particles, physics, collision, animation (up to 30 animations blended per frame on SPUs), water, path finding and streaming decompression ([PSU interview](https://www.psu.com/news/psu-talks-uncharted-with-naughty-dog-co-vice-president/)). U1 used about 30% of SPU capacity, and U2 aimed to use all of it, including post-processing on SPUs ([Engadget](https://www.engadget.com/2009-08-27-why-uncharted-2-couldnt-work-on-xbox-360.html)). U3's particle runtime was SPU-based ([GDC Vault: Effects Techniques Used in Uncharted 3](https://gdcvault.com/play/1015479/contactUs)). ND's GDC 2008 talk "The Technology of UNCHARTED: Drake's Fortune" (Balestra & Engstad) covers the original engine ([ND GDC08 page](https://www.naughtydog.com/blog/presentations_from_game_developers_conference_2008)).
- **One engine per game.** Bluepoint did **not** merge the trilogy onto one engine. Per the Eurogamer/DF interview as relayed by search extracts, each game has its own PS4-ported engine version, and only identical or deliberately aligned parts are shared. U1 was not moved to Havok because that would change its gameplay ([PSLS](https://www.playstationlifestyle.net/2015/10/19/bluepoint-games-set-work-different-kind-project-began-work-uncharted-collection-june-2014/); second-hand). This matches the three separate executables (`eboot.bin`, `big2-ps4_Shipping.elf`, `big3-ps4_Shipping.elf`). It also explains why a fix found in one game (for example U3 cloth) does not automatically apply to another.
- **PS4 runtime lineage (evidence-based inference).** The binaries contain ND's PS4-era engine infrastructure: the `ndlib\render\fg-draw-mgr.cpp` / `FrameBegin` / `GetRenderFrameParams` / `m_gfxEopTick` assert ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038)), and job threads named `NdJobWorkerThread` running `NdJob Fiber (512 KiB)` fibers ([#5099](https://github.com/shadps4-emu/shadPS4/issues/5099), [#4352](https://github.com/shadps4-emu/shadPS4/issues/4352)). The timing (work started the month TLOU Remastered shipped) and the shared Photo Mode support the reading that NDC was built on the TLOU Remastered-era ndlib, the fiber/frame-centric engine Gyrling describes. In that engine, SPU jobs became CPU fiber jobs and some work moved to GPU compute. **Neither Bluepoint nor ND has stated this directly.**
- **GPU compute.** The repo's own notes show U3 cloth runs as a GPU compute solver ("U3's cloth at ~80 FPS: the GPU hung in its solver", `gpu/shadps4/video_core/buffer_cache/buffer_cache.cpp`). shadPS4 saw NDC compute shaders reading loop bounds through dynamic `ReadConst` pointers ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038)). Both fit the reading that former SPU work moved to compute.

### Output resolution and frame rate

- **Resolution and frame rate.** All three games render at native 1080p with at least 8× anisotropic filtering, and gameplay is mostly locked at 60 fps. Rare dips to about 55 fps happen in scenes heavy with alpha effects (smoke, water) ([PSLS summary of DF](https://www.playstationlifestyle.net/2015/09/27/uncharted-nathan-drake-collection-analysis), [HotHardware](https://amp.hothardware.com/news/uncharted-the-nathan-drake-collection-heads-to-ps4-in-1080p60-glory)). V-sync is always on.
- **No 30 fps mode.** No official 30 fps option was found. A 2015 GameFAQs thread asking for one got only speculative replies ([GameFAQs](https://gamefaqs.gamespot.com/boards/164613-uncharted-the-nathan-drake-collection/72461483)). The port's README describes the "60 FPS as on PS4" default, which is accurate.
- **The brief's "1080p30" premise is wrong.** The PS3 originals were 720p30. NDC is 1080p60.

### Executable and data layout

- **Executables.** `eboot.bin` holds Uncharted 1 plus the collection menu. `big2-ps4_Shipping.elf` and `big3-ps4_Shipping.elf` hold U2 and U3. The game switches between them with `sceSystemServiceLoadExec`. shadPS4 implemented that call in [PR #3647](https://github.com/shadps4-emu/shadPS4/pull/3647) and listed CUSA02320 as a user. Testers there saw U2 and U3 hang on a grey screen when launched through LoadExec, though they ran when started directly. The port's `run.py` takes the same approach: exit code 101 means "start the other executable".
- **Patches per executable.** Patch tools needed explicit per-executable targeting: `AppElf="big2-ps4_Shipping.elf"` in GoldHEN/illusion XML, and the shadPS4 memory patcher only gained this in [PR #5184](https://github.com/shadps4-emu/shadPS4/pull/5184) (merged 29 Sep 2026, citing NDC).
- **Data folders.** `u1data/`, `u2data/`, `u3data/` hold game data, `sce_sys/` holds `param.sfo` and the app metadata (`APP_VER` is read from `param.sfo`), and `sce_module/` holds bundled PRX libraries. This matches what `run.py` and the README expect.
- **Load addresses.** Patch addresses in the community XMLs are PS4 virtual addresses with the eboot based at `0x400000`. The shadPS4 EOP patch writes `0x8d277f`, which is file/image offset `0x4d277f` + `0x400000` ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038)). The port's `patches.py` uses the same convention (`docs/DEVELOPMENT_LOG.md`).

## Naughty Dog engine internals

### Fiber job system (Gyrling, GDC 2015)

Christian Gyrling's GDC 2015 talk ["Parallelizing the Naughty Dog Engine Using Fibers"](https://www.gdcvault.com/play/1022186/Parallelizing-the-Naughty-Dog-Engine) ([slides PDF](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf), [archive.org video](https://archive.org/details/GDC2015Gyrling_201508), [ND blog](https://www.naughtydog.com/blog/2015_naughty_dog_gdc_talks_and_art_bootcamp)) describes how ND got TLOU Remastered to 60 fps on PS4. It went from a single-threaded 30 Hz PS3 design to a fiber job system running about 800–1000 jobs per frame. Points confirmed through search extracts of the slides:

- **Threads.** 6 worker threads, each locked to a CPU core.
- **Fibers.** 160 fibers: 128 with 64 KiB stacks and 32 with 512 KiB stacks. NDC's `NdJob Fiber (512 KiB)` thread label in shadPS4 logs matches the large-stack pool.
- **Jobs.** Jobs run on fibers and can yield mid-execution. Scheduling is cooperative (no preemption). Waiting on a dependency parks the fiber until an atomic counter reaches a value, and the worker thread picks up other work. Secondary reimplementations such as [FiberTaskingLib](https://github.com/galek/FiberTaskingLib) describe the same counter scheme.
- **Topics.** The talk covers the "frame-centric engine design", memory allocation patterns, and lock strategy.

**Implications for `runtime_fiber.c` / the HLE runtime:**

1. **Fibers cross threads.** A fiber suspended on worker A can resume on worker B. Anything thread-local the HLE uses must be re-fetched after every switch: TLS, the guest TCB/FS base, errno, the TEB stack bounds that Windows' unwinder and exception dispatch check, and the per-thread caches the runtime keeps. `runtime_fiber.c` already does this (`this_thread()` is `noinline` and re-reads `fiber_thread`, and `use_stack()` updates the TEB `StackBase`/`StackLimit`).
2. **The 64 KiB stacks are small.** Any HLE function that runs on the guest fiber stack, for example a library call made from a job, must not use more than a few KiB. Heavy host work (Vulkan calls, file IO, logging with big buffers) called from a 64 KiB fiber can overflow into the next fiber's stack. **Recommendation:** run heavy HLE work on a host-owned stack, or make sure Windows guard pages and `StackLimit` catch overflow.
3. **Waits must not block the worker.** ND jobs wait by switching fibers, not by blocking the OS thread. An HLE primitive that blocks an `NdJobWorkerThread` for a long time takes 1/6 of the job capacity away, and can deadlock if the job it waits for is queued behind it. Examples are a condvar wait, an `sceKernelWaitEqueue`, or a synchronous GPU read-back in a buffer-cache fault. The repo's Cartagena fix (read-backs on a side queue so the game thread is not stalled on the whole GPU queue) fits this. shadPS4 saw a U2 crash in `condvar::Wait` on `NdJobWorkerThread 0` during level load, with tight `scePlayGoGetToDoList` polling ([#4352](https://github.com/shadps4-emu/shadPS4/issues/4352)).
4. **Fibers and the red zone.** A fiber switch happens only at a `call` into `sceFiberSwitch` and similar functions, so the red zone of the caller is not live there. A **hardware fault** inside a leaf function on a fiber stack, by contrast, is dispatched by Windows on that same stack, below RSP (see [Known problems mapped to research](#known-problems-mapped-to-research)).

### Frame centric pipelining and FrameParams

- **Pipeline depth.** The talk's "frame-centric" design overlaps three stages on different frames: game logic on frame N, render/command building on N-1, and GPU execution on N-2. A community recap of the talk describes it as three frames in parallel, with the motivations "process multiple frames at once" and "memory lifetime" (search extracts of the slides). Reimplementations credit Gyrling with the same "Game (N), Render (N-1), GPU (N-2)" pipeline ([Luth README](https://github.com/Hekbas/Luth)). **Note:** the exact slide wording on FrameParams could not be fetched. Treat the details below as consistent with, not quoted from, the talk.
- **What the shipped NDC binaries confirm.** Each frame has a parameter block (`RenderFrameParams`), fetched through `GetRenderFrameParams(frame)`. `FrameBegin` frees per-frame instance data for an older frame (`frameToFreeInstancesFor`). Before reusing that slot it asserts that the GPU's end-of-pipe tick (`m_gfxEopTick`) was written, normally by the game's EOP interrupt handler ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038), comment in `src/probe.c`). The engine **never waits** there: on a real PS4, a 60 Hz flip and a GPU that keeps up guarantee the tick is set three frames later.
- **Why emulators break it.** Two mechanisms:
  1. **Ordering.** The guest's frame fence (EOP write) is the last packet of the flip command buffer, *after* the PatchedFlip NOP. If the emulator raises the flip event when it parses the NOP, the game can wake up, start the next frame and read a zero tick. [PR #5140](https://github.com/shadps4-emu/shadPS4/pull/5140) arms the flip at the NOP and signals it only after the whole DCB has run. It fixed U1 after the second cutscene, U2 after about a minute, and a CUSA02320 crash in the same area. [PR #4882](https://github.com/shadps4-emu/shadPS4/pull/4882) found the same race. Another shadPS4 fork "counts EOP flips at submit time".
  2. **Lag.** If the GPU thread falls more than about 2 frames behind (shader compilation on first run, upscaler start-up), the tick is not set yet. shadPS4's workaround is a 1-byte `jne`→`jmp` patch that removes the assert ("Remove GPU EOP tick assert (Uncharted 1)", CUSA02320 01.00 only, `0x8d277f`, [espindoIa guide](https://github.com/espindoIa/shadps4/commit/0fcbd66450b718f7271092f4913b7fc84abbb933)). This port's approach (spin until the tick appears) is safer than skipping the check: it keeps the engine's memory-lifetime guarantee. Skipping can free instance memory the GPU is still reading, which shows up as corruption, not a crash.
- **"At most one frame ahead".** The repo's `BB_MAX_FRAMES_AHEAD` (in `gnmdriver.cpp`, now off by default) and the presenter rule "the game must never wait for generated frames … Uncharted 3 asserts in FrameBegin" (`vk_presenter.cpp`) are both ways of keeping the guest's 3-frame ring valid. The pipeline is **game N, render N-1, GPU N-2**. So with the flip ordering fixed, the GPU side may lag the guest's game frame by up to about 2 frames without breaking the assert. Frame generation, extra present queues or async upscalers that hold extra swapchain images do not count toward this. Only the guest's EOP labels matter.

### Tagged heap memory

- **How it works (second-hand).** The talk's "memory allocation patterns" section is widely summarized as a **tagged heap**. Memory is handed out in fixed-size blocks, each owned by a tag such as "game frame N" or "render frame N". Per-thread or per-job linear allocators bump-allocate inside a block, and everything with a tag is freed at once when that frame's lifetime ends. The commonly cited block size is **2 MiB**, but that comes from a reimplementation's recollection, not the slides ([wb_alloc README](https://github.com/WilliamBundy/wb_alloc)). The CPU/GPU ("Onion/Garlic") split of tagged pages with GPU pages retired on the GPU timeline is how reimplementations model it ([Luth](https://github.com/Hekbas/Luth)).
- **Relevance to the port:**
  - **Frees are tied to the EOP tick.** A frame's GPU-visible memory is reused when the EOP tick says the GPU is done. Signalling EOP too early (see above) lets the engine overwrite constant buffers, skinning output or instance data that the host GPU has not consumed yet. That would show up as **one-frame visual glitches** rather than crashes. This is one candidate explanation for the U3 green/black flashes (**speculation**).
  - **Memory reuse is heavy.** Large direct-memory ranges are reused every frame, so the shadPS4 buffer cache's page tracking sees constant guest writes over GPU-read pages. The repo's notes on Cartagena ("~70 read-backs a second, 5–20 ms each") show the cost.

### Older ND tech talks and Game Engine Architecture

- **PS3-era talks.** GDC 2008, "The Technology of UNCHARTED: Drake's Fortune" (Balestra, Engstad), covers SPU job use, streaming from HDD-cached Blu-ray data and SPU decompression ([ND GDC08 page](https://www.naughtydog.com/blog/presentations_from_game_developers_conference_2008)). U2 streamed continuously with no load screens ([Engadget](https://www.engadget.com/2009-08-27-why-uncharted-2-couldnt-work-on-xbox-360.html)). This continuous level streaming is the context for the U2 `iSubMesh < m_numSubMeshInstances` assert and "white textures first" (see the mapping section).
- **Game Engine Architecture.** Jason Gregory worked on every Uncharted and both TLOU versions. The 3rd edition (2018) adds Chapter 4, "Parallelism and Concurrent Programming", and covers job systems, the game loop and real-time simulation ([Taylor & Francis](https://www.taylorfrancis.com/books/9781138035454)). The chapter text was not available here. It is the right general reference for ND-style job systems and frame timing, but it does not document NDC.
- **Not found.** No public ND talk specific to NDC, or to the PS4 GPU work in the U1–U3 remasters, was found.

## Lessons from the official PC ports

**Uncharted: Legacy of Thieves Collection (PC)** contains Uncharted 4 and The Lost Legacy, not U1–U3. Iron Galaxy ported it with Naughty Dog, and it released on Steam and Epic on 19 October 2022 ([PlayStation Blog](https://blog.playstation.com/2022/09/15/uncharted-legacy-of-thieves-arrives-on-pc-october-19-2022/), [Gematsu](https://gematsu.com/2022/09/uncharted-legacy-of-thieves-collection-for-pc-launches-october-19)).

- **What went right:**
  - Steam Deck Verified at launch ([KitGuru](https://www.kitguru.net/page/312/!https:/www.kitguru.net/gaming/mustafa-mahmoud/uncharted-legacy-of-thieves-collection-is-steam-deck-verified/)).
  - FSR 2, ultrawide support, scale sliders, **GPU and VRAM detection** and a reworked UI ([GameSpot features list](https://gamespot.com/articles/uncharted-legacy-of-thieves-collection-hits-pc-october-19-system-requirements-and-features-revealed/1100-6507543/)).
  - Mid-range GPUs held 60 fps at medium/high settings ([Laptop Mag](https://www.laptopmag.com/reviews/uncharted-legacy-of-thieves-collection)).
  - DF's verdict was reportedly "an accomplished but unambitious PC port" ([ResetEra DF thread](https://www.resetera.com/threads/digital-foundry-uncharted-legacy-of-thieves-the-df-pc-port-review-pc-vs-ps5-optimised-settings.645954/), second-hand).
- **Shader compilation.** Shaders compile up front at first boot: about 20 minutes even on a top CPU per DF notes, and around 10 minutes per GamingTrend. Skipping it was not recommended ([ResetEra recap](https://www.resetera.com/threads/digital-foundry-uncharted-legacy-of-thieves-the-df-pc-port-review-pc-vs-ps5-optimised-settings.645954/), [GamingTrend](https://gamingtrend.com/reviews/uncharted-legacy-of-thieves-collection-pc-review-drawn-back-in-again/)). DF's review build still had compilation stutter. **Lesson:** the port's first run compiles shaders on demand, which also triggers the EOP lag. A visible **pre-warm or "build shader cache" step**, or shipping or sharing pipeline caches per title and version, would reduce both stutter and frame-lag asserts.
- **VRAM.** The game overestimated available VRAM, and going over the limit caused stutter and rubber-banding ([Laptop Mag](https://www.laptopmag.com/reviews/uncharted-legacy-of-thieves-collection)). 4K maxed out 8 GB on an RTX 3060 Ti ([Digital Trends](https://www.digitaltrends.com/computing/uncharted-legacy-of-thieves-pc-best-settings-benchmarks-dlss-fsr/)). The Last of Us Part I PC (2023, also Iron Galaxy and ND) needed a series of patches, including a fix for a crash during shader building and a more accurate VRAM bar ([ND patch notes v1.0.4.0](https://feedback.naughtydog.com/hc/en-us/articles/14993933992084-The-Last-of-Us-Part-I-v1-0-4-0-Patch-Notes-for-PC), [Gameswelt](https://www.gameswelt.de/the-last-of-us/news/patch-me-if-you-can-siebtes-update-der-pc-version-verfuegbar-319950)). **Lesson:** show a VRAM budget in the launcher, warn on cards with 4 GB or less, and drop optional allocations (TAA/FSR/DLSS history buffers, frame-generation images) first.
- **Mouse.** Mouse handling took four patches to get right:
  - 28 Oct 2022: switched to raw input and **removed the frame-rate dependency of mouse camera sensitivity**. Players then found the mouse too slow.
  - 4 Nov 2022 (1.2): fixed slow movement at polling rates above 125 Hz and added a raw-input toggle (default off).
  - 16 Nov 2022: fixed loss of camera control in windowed mode and strafing camera behaviour, and added support for non-AVX2 CPUs.
  - July 2023 (1.4): fixed the camera jitter and added a mouse-smoothing option. Until then players capped the frame rate in the driver as a workaround.

  Sources: [DSOGaming](https://www.dsogaming.com/patches/uncharted-legacy-of-thieves-collection-november-4th-update-fixes-its-mouse-movement-issues/), [Prima](https://primagames.com/news/uncharted-pc-patch-1-1-release), [DSOGaming on jitter](https://www.dsogaming.com/news/uncharted-legacy-of-thieves-collection-suffers-from-mouse-camera-stutters-and-here-is-how-you-can-fix-them/), [OC3D](https://overclock3d.net/news/software/naughty_dog_finally_fixes_uncharteds_pc_stuttering_issues_with_a_new_update/).

  **Lessons for the port's U3 mouse look:**
  - Feed mouse deltas as an angle per real time (or per guest frame, scaled by the guest's delta-time), never as a stick deflection held for one frame. A stick-emulating mapping changes sensitivity with frame rate and is easy to get wrong at 120 fps.
  - Accumulate raw input between guest input polls so that high polling rates neither lose nor double-count motion.
  - Sample the accumulated delta when the guest reads the pad, not at present time, so frame generation does not cause jitter.
- **Frame cap and loading.** Reviewers missed an in-game frame-rate limiter: there was only a 30 fps lock or unlimited ([Dexerto](https://www.dexerto.com/gaming/uncharted-legacy-of-thieves-pc-review-1956589/)). DF notes also report much longer loads on PC (about 15.8 s against 2.5 s on PS5) ([ResetEra recap](https://www.resetera.com/threads/digital-foundry-uncharted-legacy-of-thieves-the-df-pc-port-review-pc-vs-ps5-optimised-settings.645954/)). The port already offers 60/120 caps. For loading, the PS4 games expect fast async reads, and file IO on job threads should never block a worker for long (see the fiber notes).
- **CPU feature requirements.** Legacy of Thieves initially required AVX2. The PS4's Jaguar CPU has AVX but not AVX2. It also supports AMD-only SSE4a (`EXTRQ`/`INSERTQ`), which shadPS4 has to emulate on Intel hosts. **Suggestion:** check whether the NDC executables contain SSE4a instructions. No handling was found in this repo's `src/`, so if they appear, Intel CPUs would fault on them. This is unverified.

## What a player needs

- **A legally owned copy.** Many players own NDC digitally because it was free to keep in January 2020 on PS Plus ([PlayStation Blog](https://blog.playstation.com/?p=220262)) and from 15 April to 5 May 2020 in Play at Home, without PS Plus ([Notebookcheck](https://www.notebookcheck.net/Sony-makes-Uncharted-The-Nathan-Drake-Collection-and-Journey-free-to-download-from-April-15-through-May-5.461671.0.html)). The project must not point to downloads or keys. Users dump their own console's copy.
- **A decrypted dump as a folder, not a PKG.** The folder needs `eboot.bin`, `big2-ps4_Shipping.elf`, `big3-ps4_Shipping.elf`, `sce_sys/` (with `param.sfo`), `sce_module/`, and `u1data/`, `u2data/`, `u3data/` (the repo README). The executables must be **decrypted** (fSELF/ELF), as made by homebrew dumpers on a jailbroken PS4. shadPS4 issues say the same, and early shadPS4 failures came from trying to install encrypted PKGs ([#611](https://github.com/shadps4-emu/shadPS4/issues/611), [#692](https://github.com/shadps4-emu/shadPS4/issues/692)).
- **Merge the update into the base game.** Dump the base game and the update (patch) and merge them, so that the folder's `param.sfo` `APP_VER` reads **01.02** and the 01.02 executables replace the 01.00 ones. Dumping tools usually produce separate "base" and "update" folders. The patch's files must overwrite the base files.
- **DLC.** NDC has no gameplay DLC; it is campaign-only. Its add-on entitlement (U4 multiplayer beta access) is long expired. Themes and avatars are not needed. Nothing beyond base + update is required.
- **Firmware modules.** shadPS4 historically asked for PS4 system modules (sys_modules) for NDC ([#1289](https://github.com/shadps4-emu/shadPS4/issues/1289)). This port's HLE replaces system libraries and links only the game's own `sce_module/*.prx` (`run.py`), so players should not need firmware files. Keep it that way: firmware files are Sony-copyrighted and harder for users to obtain legally.
- **Regions.** CUSA02320 (US), CUSA02343/02344/02826 (EU and other territories). Based on shared community patch definitions, the executables appear identical across these for the same version (inference). Region differences are likely limited to languages and audio packs, the title ID used for the save-data directory, and the age-rating screens. The standalone EU single-game releases (CUSA03280/03281/…) use a different layout and are untested with the port.

## Which version to target

- **Primary target: APP_VER 01.02, CUSA02320 or CUSA02343.** It is the final known version and what an updated console has, and most dumps will be 01.02. It contains Bluepoint's late fixes: forward-movement sensitivity, stability and visual fixes. Community patches (GoldHEN/illusion) exist for 01.02.
- **Also support 01.00.** Disc dumps without the update are common. Most public shadPS4 debugging (the #5038 addresses and the EOP patch) was done on CUSA02320 **01.00**, which makes 01.00 the best-documented version for cross-checking. A fixed-address patch from 01.00 does **not** apply to 01.02, because code moved by about `0x3C000` near the menu code.
- **Recommendations:**
  1. Keep every engine patch signature-based, as `patch_eop_tick_wait` already is.
  2. Log `TITLE_ID` and `APP_VER` at start. `probe.c` already reads them.
  3. Keep a small table of verified and unverified versions, and warn in the launcher for anything that isn't 01.00 or 01.02.
  4. Reproduce each 1.02-only crash on 1.00 to separate version-specific bugs from runtime bugs (see the mapping below).

| **U2 streaming crash** (`iSubMesh < m_numSubMeshInstances`, white textures first) on US 1.02 | U2 streams continuously with no load screens ([Engadget](https://www.engadget.com/2009-08-27-why-uncharted-2-couldnt-work-on-xbox-360.html)). shadPS4 U2 random crashes ([#5288](https://github.com/shadps4-emu/shadPS4/issues/5288), [#5107](https://github.com/shadps4-emu/shadPS4/issues/5107)). U2 level-load `condvar::Wait` with PlayGo polling ([#4352](https://github.com/shadps4-emu/shadPS4/issues/4352)). Red-zone corruption on Windows ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038), [PR #4802](https://github.com/shadps4-emu/shadPS4/pull/4802)) | "White textures first" means streamed texture or mesh data was not resident in time. Then a mesh-instance table didn't match its resource, which looks like a **load finishing late or out of order**, or a corrupted count. Suspects: (1) async file IO or PlayGo completion order differing from PS4 (`sceKernelAio*`/Fios callbacks completing before the data is visible, or completing on the wrong thread); (2) red-zone corruption of a counter in a leaf function when a page-protection fault hits mid-function (the same pattern as #5038's menu crash); (3) a guest/GPU memory race on recycled streaming buffers. Test on 01.00 and on a non-US 01.02 dump to rule out a version-specific bug. Log every vectored-exception hit with RIP and RSP around the crash |
| **U3 London bar crash** (fault at `0xd9c59b`) on US 1.02 | Same red-zone mechanism. Code offsets differ between versions (the 01.00 vs 01.02 cheat offsets). U3 crashes after FMVs without a shader cache ([PR #5140](https://github.com/shadps4-emu/shadPS4/pull/5140) comments) | Symbolize `0xd9c59b`: check whether it is a leaf function that uses `[rsp-N]` without a stack frame, which would be a red-zone victim. The London bar opens with a pre-rendered sequence and a transition, so check the video-decoder teardown and memory remap too. shadPS4 saw a device lost right after a skipped or finished cutscene, during the remap for level load ([#4353](https://github.com/shadps4-emu/shadPS4/issues/4353)). Reproduce on 01.00 |
| **>120 FPS experimental** | [Frame rate dependent logic](#frame-rate-dependent-logic-and-community-patches); Legacy of Thieves mouse frame-rate-dependency bug; a 3-frame pipeline | Above 120 fps, solver and animation constants, mouse scaling and the 3-frame ring (shorter frames, same GPU latency) all get stressed. Prefer frame generation over raw guest rate above 120 |
| **4 GB VRAM cards run out of memory** | `num_records=0xffffffff` → about 2.7 GiB clamped buffers ([#5038](https://github.com/shadps4-emu/shadPS4/issues/5038), [#4353](https://github.com/shadps4-emu/shadPS4/issues/4353), [PR #4882](https://github.com/shadps4-emu/shadPS4/pull/4882)); "a sparse buffers rewrite probably helped" (maintainer on #5038). Legacy of Thieves VRAM overestimation ([Laptop Mag](https://www.laptopmag.com/reviews/uncharted-legacy-of-thieves-collection)) | Audit the buffer cache for unbounded descriptors. Back huge ranges with sparse or host-visible memory, or with bounded windows, instead of device-local allocations. Count VRAM per category (buffer cache, texture cache, upscaler or frame-generation history) in `last_run.log`. Show a launcher warning at ≤ 4 GB (already in the README) |

## Open questions and suggested experiments

1. **Red zone.** On a crash-prone setup, log every vectored-exception entry with the faulting RIP and RSP and check whether Windows wrote within 128 B below RSP. If it did, port shadPS4's static red-zone protection ([PR #4802](https://github.com/shadps4-emu/shadPS4/pull/4802)). An alternative is to keep GPU write-tracking faults off guest threads, for example with write-watch or userfault-style tracking instead of access violations.
2. **Flip/EOP ordering.** Confirm in the port's `liverpool`/`gnmdriver` that the flip event is raised only after the trailing EOP packet, as in [PR #5140](https://github.com/shadps4-emu/shadPS4/pull/5140). Then count how often the `m_gfxEopTick` wait spins after the shader cache is warm. The target is zero.
3. **Version matrix.** Reproduce the U2 and U3 1.02 crashes on 01.00, and on EU 01.02 if the executables really are identical.
4. **Gyrling slides.** Read the [slides PDF](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf) directly. It could not be fetched here. Check the FrameParams ring size and the tagged-heap block size, and whether NDC's ndlib matches.
5. **Debug overlays.** On a private build, try ND's FPS/Task overlay (the GoldHEN cheat "Enable FPS View / Task View") to see job timings in Cartagena and London.
